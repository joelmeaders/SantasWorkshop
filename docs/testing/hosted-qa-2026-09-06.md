## Confirmed defects and remaining issues

1. **Staff child additions and edits were not persisted at check-in.**
   `ReviewPage.addChild()` and `editChild()` did not set `wasEdited`.
   They therefore used `checkIn` instead of `checkInWithEdit` unless another
   action had already marked the review as edited. The hosted test changed a
   child's first name, then checked in successfully. The original registration
   retained its old name and no `editedregistrations` record existed. The
   check-in report also counted it as unmodified. This branch fixes both paths.

2. **Password-reset mail reached Gmail Spam.** The test message from the default
   Firebase test-project sender arrived and its reset link worked. SPF and DKIM
   passed. Inbox placement and the generic test-project branding remain an
   email-configuration/delivery concern. This observation does not establish
   production delivery behavior or a specific cause for Gmail's classification.

3. **Minor copy issue.** The English signup newsletter prompt used `recieve`.
   This branch corrects it to `receive`.

4. **One customer console permission error needs follow-up.** The in-app browser
   recorded `FirebaseError: Missing or insufficient permissions` during the
   checked-in-account sign-in/return-to-home sequence. The expected closed-season
   notice appeared and the following reset and signup flows worked. No matching
   error appeared in the admin console. A repeat sign-in did not reproduce it.
   Local review found that the check-in service kept its protected read active
   after sign-out because its user-ID stream did not emit the signed-out state.
   This branch cancels that read on sign-out, with an unsubscribe regression
   test. This is a plausible cause of the observed error, not a confirmed
   diagnosis. The fix has not been verified against the deployed app.

5. **The completed-check-in notice remained English in the Spanish UI.**
   A repeat sign-in confirmed this. This branch adds English and Spanish
   translations for the title, subtitle, message, and dismissal button.

## Age-rule change after the walkthrough

The requested rule is children **11 years old or younger**, measured using the
existing December 31 cutoff. For the 2026 program, the earliest valid birthday
is January 1, 2015. A child born December 31, 2014 is ineligible.

Customer and staff copy, date bounds, and form validation are updated together.
The customer editor revalidates previously saved children when opened.
The backend canonicalizer previously accepted age 12 and mislabeled it `9-11`.
The revised validation rejects it in customer draft/submission and staff
registration/check-in paths. Standard check-in validates the stored children
and derives its totals from them. UI and backend use the configured program
year so their age rules remain consistent at calendar-year rollover.
Birthday serialization now preserves calendar dates instead of comparing local
midnight instants against UTC boundaries. Date-only values and UTC-midnight
records retain their day. Legacy non-midnight timestamps use the configured
event timezone. This does not rewrite historical records in bulk.
